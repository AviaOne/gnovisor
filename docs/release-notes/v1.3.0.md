GnoVisor v1.3.0 takes a node that catches up across halts: a node synced from
genesis, or restored from an older snapshot. It fixes
[issue #1](https://github.com/AviaOne/gnovisor/issues/1).

## Changes

- **A node catching up is taken across every halt.** In block sync, a
  gno.land node does not stay up at a halt as a live node does: it exits,
  often before GnoVisor has read the halt height. GnoVisor now reads the halt
  from what the node prints as it exits, takes the halt across as for a live
  node, and records it first, so that a restart of GnoVisor never starts the
  old version. The text is the same in every gno.land release from v1.2.0
  to v1.8.0, and GnoVisor needs nothing outside the Go standard library to
  read it, whatever the node's database.
- **Two ways to sync from genesis.** A node can start on the genesis version
  of the ledger, and GnoVisor takes it through every past halt as the network
  ran them. Or it can start on the version the chain's validator guide gives
  for a sync from genesis: GnoVisor keeps it at every past halt whose floor it
  meets, never goes back to an older version, and switches only where a
  floor asks for a newer one.
- **A manual halt stays a manual halt.** A `halt_height` in the node's
  `config.toml` that no vote and no ledger entry names is still not an
  upgrade. A node catching up that exits there is kept stopped, at any
  moment, and GnoVisor says how to go on: set `halt_height = 0`, then restart
  the service. Set at the height of a voted halt, it is that upgrade: GnoVisor
  switches, then reports that the new version stops at the same height until
  `halt_height` is removed from `config.toml`.
- **A version refused by the node is replaced.** When the old version is
  refused by the version floor of a halt (a node left stopped at a halt, for
  example), GnoVisor finds that halt by its floor and takes it across. When
  the version in service is meant for a later halt (a node restored from an
  older snapshot), GnoVisor runs the version the ledger gives for the node's
  next block. The same refusal twice on the same version is not acted on
  again.
- **No backup at a halt the network crossed long ago.** A node catching up
  takes no backup at a halt the ledger records as past (with its
  `halt_time`): a copy of the whole database at every past halt could fill
  the disk. The backup before an update in service is unchanged.

## Upgrading from v1.2.0

Replace the binary as described in the README, "Updating GnoVisor". Nothing
changes in `gnovisor.toml`. A node that GnoVisor v1.2.0 left stopped at a
halt, starting the old version again and again, is taken across by v1.3.0
once it finds that halt by its floor, in the ledger or among the versions
added by hand.
